# 振り返り問い改善スキル

## 概要

`question-types.md` に定義された問いのカタログを対話的に改善する。
ユーザーが「この問いの方向性を変えたい」というフィードバックを伝えると、
形式制約を守った新しい問いを提案し、承認後にファイルを更新する。

## 実行手順

### ステップ1：現在の問い一覧を表示

`${CLAUDE_PLUGIN_ROOT}/skills/report/references/question-types.md` を読み込み、
6カテゴリと各カテゴリの ①目的を問う／②妥当性を問う を整理して表示する。

表示後、以下を問いかける：

> 「どのカテゴリの問いを変えたいですか？また、どんな方向性にしたいか教えてください。
> （例：実装系の問いを"制約の中での判断"に焦点を当てたい、トラブル系を"次に活かせること"を引き出す方向にしたい、など）」

### ステップ2：フィードバック収集

ユーザーの要望を受け取る。以下の場合は1回だけ掘り下げ質問する：

- カテゴリが特定できない → 「どの作業のときに聞かれた問いが合わなかったですか？」
- 方向性が抽象的 → 「その問いで最終的に何を気づかせたいですか？」

掘り下げは1回まで。2回目は推測で進む。

### ステップ3：新しい問いの提案

以下の **形式制約** を守りながら提案する：

**形式制約**
- **[前置き] → [問い]** の2部構造（前置きは作業の性質を1文で限定する）
- オープンクエスチョンのみ（yes/no で答えられる問いは禁止）
- 具体的な固有名詞を含むテンプレートにする（〇〇・△△のプレースホルダーで示す）
- 「どう機能するか」「人に説明するとしたら」というフレームは使わない

**比較形式で提示する**：

```
【現在の問い】
① 〇〇を実装しようとしたとき、解こうとしていた問題は何でしたか？
② その問題に対して、〇〇という実装はどう応えていますか？

【提案A：〜方向性〜】
① 〇〇を実装したとき、どんな制約や前提の中で判断していましたか？
② その制約を踏まえて、今の〇〇という実装をどう評価しますか？

【提案B：〜別の方向性〜】（複数の解釈がある場合のみ）
① ...
② ...
```

複数の解釈がある場合のみ A/B を提示。1通りに絞れるなら1案のみ出す。

### ステップ4：反復改善

ユーザーが「もう少しこっちの方向で」「Aをベースに〇〇を変えて」と言ったらステップ3に戻る。
「これで行く」「OK」「良い」と承認されたらステップ5へ進む。

### ステップ5：question-types.md を更新

1. 承認された問いで該当カテゴリ行を上書きする
2. 更新前後の diff を表示する：

```
【変更箇所】
カテゴリ: 実装・ロジック系
① 変更前: 〇〇を実装しようとしたとき、解こうとしていた問題は何でしたか？
① 変更後: 〇〇を実装したとき、どんな制約や前提の中で判断していましたか？
② 変更前: その問題に対して、〇〇という実装はどう応えていますか？
② 変更後: その制約を踏まえて、今の〇〇という実装をどう評価しますか？
```

3. ファイルを書き込む（`${CLAUDE_PLUGIN_ROOT}/skills/report/references/question-types.md`）
4. 「次回の日報から反映されます」と伝えて完了

## NG パターン

以下の問い形式は提案しない：

| NG パターン | 理由 |
|---|---|
| 「〇〇はどう機能しましたか？」 | メリットしか引き出さない |
| 「〇〇を人に説明するとしたら？」 | 他者説明フレームは思考の深化より説明の巧みさを測る |
| 「〇〇はうまくいきましたか？」 | yes/no で答えられる |
| 「何を感じましたか？」 | 感情に寄りすぎて事実の振り返りにならない |
| 「良かった点は？」 | 評価の枠組みを押し付けてしまう |

## 注意事項

- 複数カテゴリをまとめて変えたい場合は1カテゴリずつ順番に提案・確認する
- ユーザーが「全部変えたい」と言った場合は「最も気になるカテゴリから始めましょう」と絞る
- 既存の問いの良い部分（構造や前置きの長さ等）を活かしながら方向性だけ変えることを優先する
