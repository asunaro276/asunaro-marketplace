# Claude Code 日報・振り返りスキル

## 概要

`cc-summarizer` Go スクリプトで `~/.claude/projects/` 以下のセッションファイルを並列解析し、
Claude Code作業データと今日のメモを素材にインタラクティブな振り返りを行う。
回答内容を `~/zettelkasten/Daily/YYYY-MM-DD.md` の `# ふりかえり` セクションに書き込む。

## 実行手順

### ステップ1：バイナリのパスを確定する

バイナリは同梱済みなので、ファイル存在確認やビルドは行わない。
パスだけ確定してステップ2に進む。

- Linux/macOS: `${CLAUDE_PLUGIN_ROOT}/scripts/cc-summarizer/cc-summarizer`
- Windows: `${CLAUDE_PLUGIN_ROOT}\scripts\cc-summarizer\cc-summarizer.exe`

**ステップ2でバイナリ実行に失敗した場合のみ**、以下のコマンドでビルドしてから再実行する：

```bash
cd "${CLAUDE_PLUGIN_ROOT}/scripts/cc-summarizer" && go build -o cc-summarizer ./main.go
```

### ステップ2：スクリプト実行

引数なしで実行すると「今日（UTC日付）」のセッションを対象とする。
特定日付を指定する場合は `YYYY-MM-DD` 形式で引数を渡す：

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/cc-summarizer/cc-summarizer"
# または日付指定
"${CLAUDE_PLUGIN_ROOT}/scripts/cc-summarizer/cc-summarizer" 2026-03-29
```

出力はJSONで以下の構造を持つ（`references/report-format.md` 参照）。

### ステップ3：デイリーノートの読み込み

**今日のデイリーノート**: `~/zettelkasten/Daily/YYYY-MM-DD.md`（今日の日付）を読む。
- 存在しない場合は空として扱う（エラーにしない）
- `# メモ` セクションの内容を振り返りの素材として使う

### ステップ4：インタラクティブ振り返りQ&A

以下の手順でユーザーと対話する。

#### 4-1. 作業事実の提示

CC作業データから今日のプロジェクトと作業内容を **事実として** 箇条書きで提示する。
今日のメモがあればそれも合わせて表示する。

**禁止事項**: 「〜を達成しました」「〜ができました」などの評価・要約を加えない。
何をしたかという事実だけを並べる。

#### 4-2. 振り返り問いを1問ずつ聞く

CC作業データから作業の性質を判断し、下記の「問いの種類」テーブルに従って問いを生成する。問いは **1問ずつ** 提示する。

**質問の構造**: 必ず **「前提 → 問い」** の2段構成にする。

```
[前提] {作業内容の具体的な説明。user_prompts・assistant_responses・files_accessedから
        ユーザーが何をしようとして何をしたかを1〜3文で再現する}
[問い] {作業の性質に応じた問い。固有名詞（プロジェクト名・機能名・概念）を必ず含める}
```

例：
> cc-summarizerで、複数プロジェクトにまたがるセッションファイルをgit worktreeも含めて
> 同一リポジトリとみなして集計するロジックを実装しました。
> このリポジトリ集計ロジックの本質は何だと思いますか？

例：
> SKILL.mdの質問生成の指示を、「型に固有名詞を当てはめる」方式に書き換えました。
> この変更について、インタラクションデザインの観点から説明してください。

**前提を書く目的はユーザーの「思い出し」を助けること**。
何をやっていたかをユーザーが忘れていても問いに答えられる程度の情報を含める。

**問いの目的**: 自分の判断・設計を、その作業の目的に照らして振り返るための問いを立てる。
「他者への説明」フレームは使わない。問いは常にオープンクエスチョンにする（yes/noで答えられる問いはNG）。

**問いの基本構造**: 作業の目的が会話から読み取れない・曖昧な場合は、まず目的を問い直す。
目的が明確になってから、それに対して作業内容がどう妥当だったかを問う。

```
① 目的を問う（目的が不明確なとき）
  「〇〇に取り組んでいたとき、何を達成しようとしていましたか？」
  「〇〇という作業の背景にあった課題は何でしたか？」

② 目的に対する妥当性を問う（目的が明確になったら）
  「その目的に対して、〇〇という判断はどう機能しましたか？」
  「〇〇という設計を選んだことで、何が変わりましたか？」
```

**問いの種類**: 作業内容の性質に応じて使い分ける。いずれも①→②の順で問うことを基本とする。

| 作業の性質 | ①目的を問う | ②妥当性を問う |
|---|---|---|
| 実装・ロジック系 | 「〇〇を実装しようとしたとき、解こうとしていた問題は何でしたか？」 | 「その問題に対して、〇〇という実装はどう応えていますか？」 |
| 設計・アーキテクチャ系 | 「〇〇という構造にしようとしたとき、何を優先しようとしていましたか？」 | 「その優先事項に対して、〇〇という設計はどう機能しましたか？」 |
| 判断・選択系 | 「〇〇と△△を比較していたとき、何を判断軸にしようとしていましたか？」 | 「その判断軸で見たとき、〇〇を選んだことはどう評価できますか？」 |
| トレードオフ明示系（会話からメリットとコストが両方読み取れるとき） | 「〇〇を得る一方で△△というコストが生じていますが、このトレードオフをどう捉えて意思決定しましたか？」 | 「〇〇と△△のどちらを手放すことが難しかったですか？その理由は何ですか？」 |
| 反復改善系（同じ箇所を何度も直した等） | 「〇〇を繰り返し修正していたとき、最終的に何を満たそうとしていましたか？」 | 「その基準に対して、今の状態はどこまで達していると思いますか？」 |
| トラブル・デバッグ系 | 「〇〇に詰まっていたとき、何がわからなかったのですか？」 | 「解決したあと、何が見えるようになりましたか？」 |

**トレードオフの検出**: 会話履歴から以下が読み取れる場合は「トレードオフ明示系」を優先する。
- サイズ・速度・複雑度が増加した（出力が77KBになった、ビルドが毎回走る、等）
- 何かを追加した結果、別の何かを失った・犠牲にした
- 複数の選択肢を明示的に比較していた

このとき「どう機能するか」ではなく「何を優先してそのコストを受け入れたか」を問う。
「どう機能するか」という問いはメリットしか引き出さないため使わない。

**質問の生成原則**:
- 問いの主語・目的語は必ず作業内容から取る（抽象的な「今日の作業」は使わない）
- 答えの方向を誘導しない
- 「〇〇を人に説明するとしたら」という他者説明フレームは使わない
- ユーザーがまだ言語化できていないことを引き出すことを目的とする

**フォローアップ**: ユーザーの回答が表面的・曖昧な場合は、同様に前提＋問いの構造で掘り下げる：
- 「〇〇の中で△△の部分はどう説明する？」
- 「〇〇を知らない人に説明するとしたら、何が一番難しい？」

ただし、フォローアップは1問につき1回まで。深追いしすぎない。

#### 4-3. 全問終了の確認

全問の回答が揃ったら「書き込んでもいいですか？」とは聞かずに、そのままステップ5に進む。

### ステップ5：Daily/への書き込み

`~/zettelkasten/Daily/YYYY-MM-DD.md` の `# ふりかえり` セクションを以下の内容で **置き換える**。

**置き換えの仕様**:
- `# ふりかえり` という見出し行以降をすべて新しい内容に置き換える
- `# メモ` セクションは一切変更しない
- ファイルが存在しない場合は新規作成する

**書き込む内容のフォーマット（`references/report-format.md` 参照）**:

```markdown
# ふりかえり

## Claude Code作業ログ
- **[プロジェクト名]**: [作業した内容（事実の列挙）]
- ...（セッションが0件の場合は「本日Claude Codeの利用なし」）

## 振り返り

**Q: [問い1]**
[ユーザーの回答をそのまま記録。要約しない。フォローアップがあった場合はそのやり取りも含める]

**Q: [問い2]**
[ユーザーの回答]

...
```

書き込み完了後、ファイルパスをユーザーに伝える。

## エラーハンドリング

- `go` がインストールされていない場合：「Goのインストールが必要です（https://go.dev/dl/）」と案内する
- セッションが0件の場合：振り返りは続行する（Claude Code未使用の日もある）
- コンパイルエラーの場合：エラーメッセージをそのまま表示して対処法を提案する

## 注意事項

- セッションファイルはUTCタイムスタンプで記録されているため、日本時間と最大9時間ずれる場合がある
- 機密情報（APIキー、パスワードなど）と思われる内容は日報に含めない
- `Warmup` メッセージのセッションは自動でスキップされる
- ユーザーの回答は要約せず、語尾や言い回しも含めてそのまま記録する
